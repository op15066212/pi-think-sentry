## 二、反对的那条：判据的漏洞不是「行数过半」，是「行内只放一个汉字」

你的诊断写「判据是行级的，它只改那几行，其余 73% 一字不动」。一半对：
**它连那几行都不用改**——它只要在每行里塞一个汉字，那一行就归成「中文行」。

证据（判绿即 clean 的 508 块，逐行统计）：

```
中文行 8604 个，平均 43.7 字符
非中文行  314 个，平均 30.2 字符
→ 96.5% 的行「含汉字」，行级投票几乎从不失败；但整块字符比中位数在 0.1–0.3
```

注意中文行**比**非中文行长（43.7 > 30.2），所以「短行凑票」的解释不成立；
唯一能同时满足「96.5% 的行含汉字」与「字符比 0.276」的形态是**行内混排**：
`然后 the 文件 should be 读取 一次`。这就是「刚好过线」的真实机制。

而 L2 的三种候选触发条件（累计判红 / 本块 CJK 比 < 0.15 / 超 2000 字符且 CJK < 0.2）都要求**先判红**——
78% 的污染块从不判红（508 个 clean 块里 397 个字符比 < 0.4），L2 对它们一次都不会触发。

### 替代处方（同一份判据，改一行）

`langJudge` 现在：`isTarget = countCjk(line) > 0`。改成「行内汉字占该行字符的比例 >= 0.3 才算目标行」：

```
规则                              红数    命中(<0.3 污染块)   误杀(>=0.6 真中文)
当前：行内有汉字即中文行              2       2/264              0/11
R1：行内汉字占该行字符 >= 0.3        102      97/264              0/11
R2：行内汉字占该行字符 >= 0.5        320     217/264              0/11
R3：无拉丁字母（纯中文行）            394     224/264              0/11
```

**四个候选的误杀都是 0/11**，因为判据是相对比较（非中文行 > 中文行），真中文块里中文行占绝对多数。
所以收紧的代价不是误伤，是**拦截次数**：R1 让红块 2 → 102（50 倍），拦截会跟着涨——这必须在同一版里处理（见 Q3）。

## 三、三个问题

### Q1 L2 的触发条件选哪个
**现在哪个都不该选，因为 L2 不该现在做。** 但如果必须落一个数，我选你候选里的第三个的改法：

```
本块 CJK 字符比 < 0.3 且块长 > 800 字符
```

理由三条，都可复跑：

1. **它在现有数据上有样本**：533 块里满足的有 258 块（字符比 < 0.3 且 > 800 字符的组合我没有单独数，但字符比 < 0.3 有 264 块），不是 0。
2. **它测的是「模型读到的英文样本」本身**，不是「模型已经红过几次」——后者依赖判据灵敏度，判据一改这个数就全变。
3. 你另两个候选我实测过可用性：**「累计判红 >= 3」其实可用**（红块 14 个，累计到 3 之后每次红都触发 → 约 12 次），
   你把它和「连续 2 次」一起否掉了，但两者的触发面差一个数量级：连续 = 1 次（还是会话开头），累计 = 12 次。

### Q2 替换「判红那一块」还是「本轮所有块」
**实现成「所有块」，但别声称这个选择有数据依据。**

实测 533 个 thinking 块 / 636 条 assistant = **0.84 块/条**，`src/features/strip.ts:95` 的注释也写了
「31556 条 message 全部只有一个 thinking 块」。所以在现有数据上两个选项**不可区分**——
选「所有块」的理由是将来多块时只换红块会留下同轮的英文样本，而这正是要消灭的东西。

判据（可复跑）：构造一条 message，content 里两个 thinking 块，一个判红一个判绿；
改写后两块都不该还有英文行——这条现在写不出来，因为功能还没有。

### Q3 拦截本身要不要保留
**保留，但必须加冷却，否则判据一收紧就变成死循环。**

`src/index.ts:245-256` 现在明写「没有次数上限，也没有冷却」：判红一次，之后每一次 tool_call 都 block。
当前只在 22 次上出现，因为判红罕见；R1 之后红块 102 个，同一次工具调用被反复打回的概率会变高。

改动条款：**同一个 toolCallId 只拦一次**。第二次放行并记 `redCalls`（分母照旧），reason 里追加一句「已提示过一次」。
判据：连发三次 tool_call 且判据恒红 → 现在 block 3 次，改后 1 次 + redCalls 增 1。

保留的理由不是「惩罚」，是**测量**：22 次拦截里 14 次改善（+0.19）是这个插件唯一的有效性证据。
去掉它，L1/L2 就没有基线可比。

## 四、四条风险，逐条判

| 风险 | 我的判 | 依据 / 改动 |
| --- | --- | --- |
| 1 thinkingSignature | 成立，但**字段名与判法都要改** | 实测 533 块 `thinkingSignature` 全是 `"reasoning_content"`（常量），你的判断对。但判据不能硬编码这个串：应记「本会话第一次见到的值」，值变了就不改写。**且不改写时必须计数**（`skippedBySignature`），否则「改写生效」那条判据在签名变了的机器上永远静默绿。 |
| 2 丢工作记忆 | 成立，你的缓解**不成立** | 「提示里带『你正在做的事见上一条工具结果』」是元指令，模型会把它当思路续写——这正是风险 3 的形态。改用「保留原块最后 3 行 + 提示」，判据：替换后原块最后一行仍在。更好的做法是先 L1（不丢记忆），L2 只在同一 toolCall 重试时用。 |
| 3 轮换池被模仿 | 成立，且「混入一条不要模仿」**会加重它** | 那句本身是元指令，最容易被照抄。改用「引用该块自己的英文行」：提示 = 原文前 3 行 + 「这几行是英文，改写它们」+ 「这是外部提示」。每轮唯一、不可模仿，也不需要轮换池与 turn 序号取模。 |
| 4 缓存失效 | 成立，但**不用做实验，现成 usage 就有** | 全会话 636 条 assistant：cacheRead 114,042,240 / 总输入 116,651,921 = **97.76%** 命中；平均单条输入 179K token；平均 thinking 块 910 字符（≈300 token）。改动发生在落盘后的那条消息，失效范围是它本身 → 每次改写 ≈ 单轮输入的 0.17%。可忽略，但要记账：`cacheRebuildTokens` 每改写一次加一个块长。 |

## 五、我还要补的一条：L1 已经实现了，只是没开

`src/features/inject.ts` 的 `applyWith` 就是 L1：追加到**最后一个 thinking 块的末尾**、按 `endsWith` 幂等、
而 `judges.ts` 的 `dropInjectedTail` 已经把末尾那一段从投票里剥掉（防自锁）。
`settings.json` 现在是 `inject: { on: true, text: "" }`——**开着，但文案为空，所以什么都不做**。

也就是说：L1 的落地成本是**填一个字符串**，不是写代码。你要的「轮换」才需要代码，而我上面建议不要轮换池。

所以顺序我建议这样：

1. `inject.text` 填一条（引用原文的那版），零代码，今天就能看效果；
2. 同版改 `langJudge` 的行内判据（R1）+ 拦截加冷却；
3. 跑一周，看红色块数、拦截次数、改善率从 +0.19 走到哪；
4. L2 用「字符比 < 0.3 且 > 800 字符」做触发，只在第 3 步证明 L1 不够时上。
